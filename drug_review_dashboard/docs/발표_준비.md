# 발표 준비 자료 — 아키텍처 · 핵심 포인트 · 예상 Q&A

> 발표 5분 + 질문 2분 대비. 대본은 `발표_대본.md`, 특성 상세는 `특성_엔지니어링.md` 참고.

## 1. 강조해야 할 핵심 포인트 (점수가 나오는 곳)

1. **누수 발견·제거 스토리** ⭐ 최대 무기 — "처음 99.6%를 의심했고, 원인(라벨 정의 컬럼 학습)을
   찾아 제거한 뒤 정직한 90.2%를 보고한다." 등급표 '상'의 "개선 시도 흔적" 그 자체.
2. **EDA → 특성 → 모델의 연결 서사** — 모든 특성에 EDA 근거가 있다 (특성_엔지니어링.md 표).
   "그래프를 그렸더니 → 이런 패턴이 보여서 → 이 특성을 만들었다"로 말하기.
3. **약한 라벨링** — 정답이 없는 현실 데이터를 교수님 피드백대로 투명한 규칙으로 해결.
4. **베이스라인 비교** — 단순 규칙(rating≤3, F1 0.62)을 RF(0.90)가 크게 이김 → ML의 존재 가치 증명.
5. **시연 안정성 설계** — 4단계 데이터 폴백, LLM 3단계 폴백, 18개 단위 테스트. "남이 켜도 돈다."

## 2. 아키텍처 (그림으로 설명)

```
[R&D]  notebooks/EDA_and_Preprocessing_Analysis.ipynb   ← 로직 정의·검증
            │ 같은 src/ 모듈 import (Single Source of Truth)
[핵심]  src/ ── data_loader (4단계 폴백 적재·정제)
            ├─ features    (11개 새 특성 + 약한 라벨, 누수 경계선)
            ├─ data_cache  (prepare_data 순수함수 + @st.cache_data 래퍼)
            ├─ modeling    (TF-IDF+RF 파이프라인, HGB·베이스라인 비교)
            └─ llm_helper  (route_chat: Ollama→OpenAI→규칙)
            │
[Production] app.py + pages/ 5개 (모두 같은 캐시 항목 공유)
```

- **왜 이 구조인가**: 노트북에서 검증한 코드를 앱이 복사가 아니라 **그대로 import** →
  노트북과 앱의 특성 값이 항상 동일(shape·dtype·해시 확인). 로직 중복·불일치 원천 차단.

## 3. 데이터 흐름 요약

1. `load_drug_reviews(max_rows=50k)` — 로컬 → 캐시 → 네트워크 → 데모 순서로 적재, 컬럼 표준화·HTML 복원.
2. `add_features()` — 11개 새 특성 + `risk_label`(약한 라벨) 생성.
3. `get_prepared_data()` — 결과를 Streamlit 캐시에 1회 저장, 5개 페이지 공유.
4. 모델 서비스: `train_risk_model()`(캐시) → 사용자 입력 → `make_prediction_frame()` → `predict_risk()`.
5. 챗봇: `build_drug_context()`(약물 리뷰 근거 요약) → `route_chat()` → 실패 시 규칙 답변.

## 4. 핵심 의사결정 요약 (왜?)

| 결정 | 이유 |
|---|---|
| 약한 라벨링 | 정답 ADE 라벨이 없음. 교수님 피드백 — 규칙 기반 약한 라벨이 현실적 |
| 라벨 정의 3컬럼 학습 제외 | 넣으면 Acc 99.6%/AUC 1.0 (규칙 암기). 빼면 정직한 96.6%/F1 0.90 |
| `rating`은 유지 | 사용자 직접 입력 신호 + 단독으로는 라벨 복원 불가 + 베이스라인 비교로 검증 |
| RandomForest 배포 | 빠른 단건 추론, feature_importances_ 해석 용이. HGB는 성능 더 좋아 비교군·향후 후보 |
| Ollama 우선 LLM | 무료·로컬·오프라인 시연 가능. OpenAI는 백업, 최후엔 규칙 답변 — 절대 안 죽음 |
| 중앙 캐시(data_cache) | 페이지별 중복 로딩 5회 → 1회. 페이지 전환 즉시 |
| 이미지 인식 격리 | 교수님 피드백 — 텍스트가 핵심, 이미지는 보너스 탭 + 파일명 폴백 |

## 5. 예상 발표 질문 & 답변 (Q&A)

**Q1. 정답 라벨이 없는데 어떻게 분류 모델을 만들었나요?**
> 심각 키워드 등장 OR (평점≤3 AND 증상 키워드)라는 투명한 규칙으로 약한 라벨을 만들었습니다.
> 교수님 피드백을 반영한 설계이고, 규칙이 코드(`build_target`)에 그대로 공개되어 있어 재현 가능합니다.

**Q2. 정확도가 96%인데 왜 "정직한" 성능이라고 하나요? / 왜 99%가 아니죠?** ⭐ 가장 중요
> 처음엔 99.6%가 나왔는데, 라벨을 정의한 컬럼(키워드 수·저평점 플래그)이 학습에 들어가
> 모델이 라벨 규칙을 암기한 타깃 누수였습니다. 그 3개 컬럼을 제외하고 리뷰 원문 TF-IDF
> 중심으로 재학습한 결과가 96.6%/F1 0.90입니다. 숫자는 내려갔지만 진짜 일반화 성능입니다.

**Q3. 그럼 rating도 라벨에 쓰였는데 왜 학습에 남겼나요?**
> 라벨의 clause B는 "평점≤3 **AND** 증상 키워드"입니다. 키워드 수를 빼면 rating 단독으로는
> 라벨을 복원할 수 없고, 실서비스에서 사용자가 직접 입력하는 진짜 신호입니다.
> 실제로 rating만 쓰는 규칙 베이스라인은 F1 0.62에 그쳐, 모델이 rating 암기로 점수를
> 낸 게 아님을 비교표로 증명했습니다.

**Q4. 새로 만든 특성은 무엇인가요?**
> 원본 7컬럼에서 11개 수치 특성을 만들었습니다. 예: 약물별 IQR 기준 저평점 이상치
> (같은 2점도 평균 9점 약물에선 이상치), 리뷰 길이·느낌표·대문자 비율(위험군 리뷰가
> 길고 격하다는 EDA 발견), 긍정 키워드 수(안전군 어휘 발견). 전부 EDA 근거가 있습니다.

**Q5. 이 모델/LLM은 뭘 입력받아 뭘 출력하나요?**
> ML: 약물명+증상 텍스트+평점 → 위험 확률(%)과 위험군/안전군 판정.
> LLM: 예측 결과+리뷰 통계를 컨텍스트로 받아 한국어 상담 리포트/챗봇 답변 생성.
> LLM이 없으면 자동으로 데이터 통계 기반 규칙 답변으로 대체됩니다.

**Q6. EDA에서 가장 놀란 발견은?**
> 상관 히트맵에서 severe_keyword_count와 라벨의 상관이 0.64로 너무 높았던 것 —
> 그게 누수를 발견한 단서였습니다. EDA가 모델 디버깅으로 이어진 경험입니다.

**Q7. HGB가 더 좋은데 왜 RF를 배포했나요?**
> 단건 추론 속도와 feature_importances_ 해석 가능성 때문입니다. 서비스 화면에서
> "어떤 단어가 위험 판정에 기여했는지" 보여주는 게 수업 시연 목적에 더 맞다고 판단했고,
> HGB는 비교표에 함께 보고해 향후 배포 후보로 남겼습니다.

**Q8. 위험군 Recall이 83%면 17%는 놓친다는 뜻 아닌가요?**
> 맞습니다. 한계로 명시했고, 의료 도메인은 놓침(FN)이 더 위험하므로 향후 과제로
> Recall 우선 threshold 튜닝을 제시했습니다. 또 이 서비스는 진단이 아니라
> "의료진 상담으로 연결하는 참고 신호"로 포지셔닝했습니다.

**Q9. 키워드 사전 기반이면 새로운 표현은 못 잡지 않나요?**
> 라벨은 키워드 기반이라 그 한계가 있습니다(보고서 한계 2번 — "heart pounding out of
> my chest"는 위험도 0.39로 미감지된 실측 사례도 보고서에 적었습니다). 다만 모델 입력은
> TF-IDF 1,500차원이라 사전에 없는 단어도 학습하며, 근본 해결은 임베딩 기반 일반화로
> 향후 과제에 제시했습니다.

**Q10. 데이터 라이선스는 확인했나요?**
> 원본 UCI 배포본은 CC BY 4.0, Kaggle 재배포본은 더 엄격한 CC BY-NC-SA 4.0이어서
> 엄격한 쪽을 따랐습니다. 그래서 데이터는 저장소에 포함하지 않고 출처 URL만 명시했습니다.

**Q11. 앱이 데모 데이터로 켜지면 어떻게 하죠? (시연 사고 대비)**
> 적재가 로컬→캐시→네트워크→데모 4단계 폴백이라 캐시가 있는 한 데모로 떨어지지 않습니다.
> 만약 떨어지면 화면 상단에 원인 경고가 떠서 바로 알 수 있고, Clear cache 후 재실행하면 됩니다.
