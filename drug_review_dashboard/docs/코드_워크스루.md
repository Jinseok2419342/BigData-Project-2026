# 코드 워크스루 — "이 코드가 뭘 하는지" 설명용

> 루브릭: "AI로 코드를 짜도 되지만, 발표에서 이 코드가 뭘 하는지 설명 못 하면 감점."
> 이 문서는 파일별로 핵심 함수와 설계 이유를 정리해 그 질문에 바로 답할 수 있게 한다.

## 전체 데이터 흐름 (한 장 요약)

```
 KaggleHub CSV (215k행, 7컬럼)
        │  src/data_loader.py  load_drug_reviews()
        │    ① data/ 로컬 → ② 캐시 직접 읽기 → ③ 네트워크 → ④ 데모 (4단계 폴백)
        │    + 컬럼 표준화·HTML 엔티티 복원·빈 리뷰 제거
        ▼
 src/features.py  add_features()
        │    11개 새 특성 + 약한 라벨(risk_label) 생성
        ▼
 src/data_cache.py  prepare_data() ──(순수 함수, 노트북도 동일 호출)
        │            get_prepared_data() = @st.cache_data 래퍼 (앱 전용, 5페이지 공유)
        ▼
 ┌──────────────┬──────────────────┬──────────────┐
 │ pages/1·2·4   │ pages/3 모델 서비스 │ pages/5 챗봇   │
 │ EDA·시각화·조회│ src/modeling.py   │ src/llm_helper│
 │               │ RF 학습→단건 예측  │ route_chat()  │
 └──────────────┴──────────────────┴──────────────┘
```

## src/data_loader.py — 적재와 정제

| 함수 | 하는 일 | 설계 이유 |
|---|---|---|
| `load_drug_reviews()` | 4단계 폴백으로 데이터 적재 | 발표 중 네트워크가 죽어도 시연이 멈추지 않게 |
| `_load_kaggle_cache()` | KaggleHub 캐시 CSV를 **직접** 읽음 | kagglehub는 캐시가 있어도 매번 네트워크 확인 → 일시적 오류로 데모 데이터로 떨어지는 사고 방지 |
| `_standardize_columns()` | 컬럼명 통일, HTML 엔티티 복원, 타입 변환 | EDA에서 발견한 품질 이슈(`&quot;` 등)를 적재 단계에서 일괄 처리 |
| `_generate_demo_data()` | 시드 고정 가짜 데이터 480행 | 최후의 폴백 — 어떤 환경에서도 앱이 열림 |

## src/features.py — 특성 엔지니어링 (상세: 특성_엔지니어링.md)

| 함수 | 하는 일 | 설명 포인트 |
|---|---|---|
| `count_keywords()` | 사전 키워드의 "종류 수" 카운트 | 세트당 정규식 1개 사전 컴파일(`lru_cache`) → 5만 행에서 ~4배 빠름. `\b` 단어 경계로 "er"가 "better"에 오탐되지 않음 |
| `build_target()` | 약한 라벨 생성 | `(심각 키워드) OR (평점≤3 AND 증상 키워드)` — 교수님 피드백 반영 |
| `compute_drug_stats()` | 약물별 Q1/Q3/IQR/이상치 기준 | "낮은 평점"을 약물별 기준으로 맥락화. 5건 미만 약물은 전체 분포로 보정 |
| `add_features()` | 특성 13개 + 라벨 생성 | 노트북·앱 공유(SSOT). ①정제 ②언어신호 ③키워드 ④라벨 ⑤약물 통계 순 |
| `make_prediction_frame()` | 사용자 입력 1건 → 모델 입력 행 | 텍스트 특성은 1행만 계산, 약물 통계는 전체에서 조회. 새 약물은 전체 분포로 대체(콜드 스타트) |
| `MODEL_FEATURES` / `LABEL_DEFINING_FEATURES` | 누수 차단 경계선 | **이 두 리스트가 프로젝트 핵심 의사결정의 코드 구현** |

## src/data_cache.py — 중앙 캐시 계층

- `prepare_data()`: 적재→특성화의 순수 함수. Streamlit 없이도 동작 → 노트북이 그대로 호출.
- `get_prepared_data()`: 위 함수의 `@st.cache_data` 래퍼. **5개 페이지가 같은 함수 객체를
  같은 인자 `(max_rows, False)`로 호출**하므로 캐시 항목 1개 공유 → 페이지 전환 즉시.
- 과거에는 페이지마다 자체 `get_data`가 있어 같은 작업이 최대 5번 반복됐다(개선 흔적).

## src/modeling.py — 모델 학습·예측

| 함수 | 하는 일 | 설명 포인트 |
|---|---|---|
| `_build_preprocessor()` | TF-IDF(1~2gram, 1500) + StandardScaler | **MODEL_FEATURES만 입력** — 누수 차단의 실제 지점 |
| `train_risk_model()` | 층화 샘플링→75:25 분리→RF 학습→HGB·베이스라인 비교 | RF 선택 이유: 빠른 단건 추론 + `feature_importances_` 해석. 베이스라인(rating≤3)을 이겨야 텍스트의 예측 가치 증명 |
| `predict_risk()` | 단건 추론, 확률→0.5 기준 판정 | 학습과 동일한 입력 형태 보장 |
| `_feature_importance()` | 상위 20개 특성 중요도 | 누수 제거 후 hospital/er/suicidal 등 의미 토큰이 상위 |

## src/llm_helper.py — LLM 라우팅과 폴백

| 함수 | 하는 일 | 설명 포인트 |
|---|---|---|
| `route_chat()` | **모든 LLM 호출의 단일 관문** | Ollama(로컬, 무료) → OpenAI(키 있을 때) → None. 각 단계가 예외를 삼키므로 앱은 절대 죽지 않음. 18개 단위 테스트로 검증 |
| `build_drug_context()` | 약물별 리뷰 통계·키워드·예시 요약 | 챗봇 답변을 데이터에 **근거(grounding)** 시켜 환각 방지 |
| `answer_drug_question()` | 질문→LLM 시도→실패 시 규칙 답변 | 오프라인에서도 챗봇이 항상 응답(시연 안전) |
| `build_rule_based_report()` | 통계 기반 상담 리포트 | LLM 성공 여부와 무관하게 항상 제공되는 기본 리포트 |
| `try_ollama_vision()` | 약통 이미지 → 약물명 매칭 | 보너스 경로. 실패 시 파일명 매칭으로 폴백 (교수님 피드백 3번: 메인과 격리) |

## pages/ — 화면 구성

| 페이지 | 역할 | 데이터 출처 |
|---|---|---|

## tests/test_llm_routing.py — 무엇을 어떻게 테스트하나

- 네트워크 경계(`_openai_chat`, `_ollama_chat`, 키 해석기)를 **monkeypatch로 가짜 함수로 교체**
  → 실제 API 키·Ollama 서버 없이 라우팅/폴백 로직만 순수하게 검증.
- 18개 테스트: 제공자별 우선순위, 키 없음/호출 실패 시 폴백, 전부 실패 시 규칙 답변, 키 해석.
- 실행: `python -m pytest -q` (프로젝트 폴더에서).
